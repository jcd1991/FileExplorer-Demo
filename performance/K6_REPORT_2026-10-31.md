# k6 findings — October 31, 2026

The API passed upload and mutation integrity checks. The actionable performance finding is paging-cache churn: the global two-view cache evicted three snapshots during 100 workflows at five concurrent users. A direct client that required every snapshot to remain valid completed 97/100 workflows; the browser-equivalent refresh/retry completed 100/100.

## Scope and environment

Local Release build, target net8.0; .NET SDK 10.0.403, runtime 8.0.33; k6 2.3.0; MacBookPro18,3, arm64, eight CPUs, 16 GiB RAM. The harness launched/stopped its own loopback server using isolated generated data. No latency threshold was configured. These short, same-host tests do not establish an SLO, sustained throughput, network capacity, or browser rendering performance.

Fifteen k6 runs were executed: initial smoke; six 20-upload baselines (three diagnostics off/on pairs); 100- and 500-upload concurrent profiles; a 20-upload 10 MiB profile; one 100 MiB upload; workflow smoke; direct concurrent workflow; client-equivalent concurrent workflow; and a final harness smoke.

**743/743 standalone measured uploads succeeded.** Including workflows, **941 measured uploads succeeded**, with no upload failures. All fifteen outside-workload upload/download verification checks passed. Workflow checks additionally verified SHA256 after file copy/move and nested contents after folder copy/move. No workflow-created files or temporary stages remained after cleanup. Generated batch data was removed; reports, logs, and verification evidence were retained.

## Mixed workflow measurements

Each iteration browsed and searched a 5,000-file catalog; fetched snapshot page two; uploaded 1 MiB; copied, moved, downloaded and hash-verified a file; copied/moved a folder and verified its nested file; and deleted the generated files/folder.

The direct API run made 1,270 requests: three HTTP 409 snapshot evictions stopped three iterations before upload/mutation. Its checks/HTTP/workflow thresholds failed. All 97 workflows that reached mutation completed successfully. This failure must not be mistaken for an upload failure—the upload-only report correctly reports zero failed uploads while the full workflow failed.

The client-equivalent run made 1,303 requests and completed 100/100 workflows, including three expected HTTP 409 responses followed by successful refreshes. Its expected-response configuration treats those protocol-defined 409s as recoverable; they are still counted and reported as snapshot expirations. All 1,903 checks passed. This matches the existing SPA fallback rather than removing the observed cache pressure.

## Findings and next steps

1. The two-slot cache is small enough to churn at five concurrent users. Retain the current fallback. If multi-client performance becomes a requirement, measure a byte-bounded larger cache or client-scoped allocation before changing policy. The app remains a documented single-user exercise; these eviction responses follow the current API contract.
2. Browse/search dominate the measured mixed workflow; cache hits are much cheaper, but an eviction adds another scan (about 94 ms here). Mutation latency and integrity checks showed no observed failure in these runs.
3. Higher upload concurrency increased latency: the expanded ten-VU run had p95 52.96 ms versus a median baseline p95 of 7.26 ms. This is an observation, not a failed latency gate. Earlier README timings are not a controlled before/after baseline; no code regression is established.
4. A representative-host duration test with CPU, RSS, disk I/O, and free-space sampling is needed before attributing bottlenecks or claiming sustainable capacity. No such measurements or production claims are inferred here.
